# 项目说明与进度 — Local RAG System

> 本地 RAG 知识问答系统。上传文档 → 自动向量化入库 → 提问 → LLM 结合知识库回答，全程本地运行。

---

## 启动命令

按顺序执行：

```bash
# 1. 激活 conda 环境
# 2. 启动 Qdrant 向量数据库（Docker）
# 3. 启动 FastAPI 后端（:8000）
conda activate localrag
docker compose up -d
uvicorn app.main:app --reload

# 4. 启动前端（:5173，新终端窗口）
cd frontend
npm run dev
```

> 确保 LM Studio 已打开，且以下两个模型已加载：
> - `qwen/qwen3-v1-8b`（LLM）
> - `text-embedding-bge-small-zh-v1.5`（Embedding）

快速验证：

```bash
curl http://127.0.0.1:8000/health          # 健康检查
curl -X POST "http://127.0.0.1:8000/documents/upload" -F "file=@somefile.pdf"  # 上传文档
```

**Sprint 4 — 智能查询处理 + 前端视觉升级**

查询处理（Pre-Retrieval Query Processing）：
- **意图识别**：LLM 自动识别用户意图（问答/总结/对比/事实查找 4 类）
- **查询改写**：LLM 将模糊问题改写为更清晰、更适合向量检索的查询语句
- **失败回退**：LLM 调用失败时静默降级为原始查询
- 新增 `app/rag/query_processor.py` 模块

前端视觉升级（"Editorial Ink" 深色主题）：
- CSS 自定义属性设计系统，Plus Jakarta Sans 字体
- 玻璃效果顶栏和输入区，侧边栏不透明表面
- CSS 从 ~2000 行精简至 ~800 行

**Sprint 5 — 批量摄入 + 增量更新 + 查询日志**

批量摄入（`ingest.py` + `app/rag/ingestion/`）：
- **CLI 脚本**: `python ingest.py --input_dir data/engineering --batch_size 64`
- **增量更新**: SQLite checksum 数据库，MD5 变更检测，文件未改则跳过
- **批量 embedding**: 直接调用 OpenAI-compatible API (input: list[str])，每批 64 条
- **批量写入**: Qdrant `upsert` 按 500 点/批拆分，避开 32MB payload 限制
- **Markdown 标题保留**: MarkdownHeaderTextSplitter 保留 H1/H2/H3 层级
- **统一 pipeline**: 上传 API 与 `ingest.py` 共用同一套 load→split→batch embed→bulk upsert 流程
- 新增支持格式: `.docx` (Docx2txtLoader), `.markdown`

查询日志（`app/rag/query_logger.py`）：
- **终端输出**: 简短一行摘要（时间、intent、top chunk、答案预览）
- **JSONL 持久化**: `logs/history/rag_queries.jsonl` 记录完整查询轨迹（问题、改写后查询、检索结果含 score + file_path + chunk_index、最终答案）
- SourceChunk 扩展: 新增 `file_name`, `file_path`, `chunk_index` 字段

**Sprint 6 — RAG 管道智能化 + 对话上下文 + SSE 流式输出**（2026-05-20）

核心改进三大块：

1. **RAG 路由门控**（`query_processor.py`）
   - **Layer 0 关键词预过滤**：正则匹配问候/致谢/道别/元问题，零 LLM 调用即时响应
   - **Layer 1 LLM 统一路由**：单次 LLM 调用同时输出路由决策（`ROUTING: YES|NO`）+ 意图分类 + 改写查询或直接回答
   - 分流逻辑：非 RAG 查询跳过向量检索，直接返回 LLM 回答（从 2 次 LLM 调用降为 0-1 次）

2. **多轮对话上下文**（全新会话管理）
   - API 新增 `conversation_id`（后端生成 12 位 hex UUID）+ `history`（前端发送最近 10 条消息）+ `Message` 模型
   - 历史注入两处：query_processor（代词消解，如 "它" → "RAG"）+ RAG prompt（对话连续性）
   - Token 预算 ~2048，旧消息优先丢弃。"New Chat" 重置 `conversation_id` 为 null

3. **SSE 流式响应**（提升感知速度）
   - 新增 `POST /rag/query/stream` 端点，FastAPI `StreamingResponse` + LangChain `chain.astream()` 逐 token 推送
   - 前端 `fetch` + `ReadableStream` 解析 SSE 协议，token 实时渲染，首 token 到达即隐藏 loading

附加优化：
- 嵌入缓存：`CachedOpenAIEmbeddings`，线程安全 LRU（256 条目，MD5 键），重复查询跳过 embedding API
- 异步日志：`log_rag_query()` 移至 daemon 线程，HTTP 响应不再阻塞于磁盘 I/O
- 压缩查询处理提示词：~60 tokens（原 ~150 tokens）
- 前端新增路由指示器（"已搜索文档" / "直接回复" / "快速回复" 彩色标签）+ `@rag` 前缀强制检索

## 系统架构

### 宏观数据流

整个系统围绕两条核心数据流运转：

**摄入流**（离线，批量/单文件）：

```
文件系统                     Python 后端                      向量数据库
───────                    ────────────                     ──────────

PDF/TXT/MD/DOCX  ──→  Loader（解析） ──→ Splitter（切分）
                                            │
                                    Batch Embedder（批量向量化）
                                            │
                                    Bulk Writer ────────→ Qdrant 向量库
                                            │
                                    Checksum Store ────→ SQLite（MD5 增量）
```

**查询流**（在线，同步/流式）：

```
浏览器                     FastAPI                        LLM + Qdrant
──────                    ───────                        ────────────

用户输入 ──→ API 层 ──→ Service 层 ──→ Query Processor（路由门控）
                                            │
                              ┌─────────────┴─────────────┐
                              ▼                           ▼
                         needs_rag?                   needs_rag?
                           YES                           NO
                              │                           │
                              ▼                           ▼
                      Retriever ──→ Qdrant          直接返回答案
                              │
                              ▼
                      Chain（Prompt + LLM）
                              │
                              ▼
                      答案 + Sources ────→ 前端渲染
```

### 路由门控决策树

这是系统智能化的核心——不是一个查询走到底，而是先判断"这问题需要翻文档吗"：

```
                         ┌──────────────┐
                         │   用户输入     │
                         └──────┬───────┘
                                │
                    ┌───────────▼───────────┐
                    │ force_rag == true?     │
                    │ (前端 @rag 前缀)       │
                    └───────────┬───────────┘
                          YES   │   NO
                          │     │
                          │     ▼
                          │  ┌──────────────────────┐
                          │  │ Layer 0: 关键词匹配?   │
                          │  │ regex: 你好/谢谢/再见  │
                          │  │ /你是谁/帮助/...等    │
                          │  └──────────┬───────────┘
                          │       匹配   │   不匹配
                          │        │     │
                          │        ▼     ▼
                          │   ┌────────┐ ┌──────────────────────┐
                          │   │greeting│ │ Layer 1: LLM 统一路由  │
                          │   │0 LLM   │ │ 单次调用同时输出:      │
                          │   │调用    │ │ ROUTING + INTENT       │
                          │   └────────┘ │ + QUERY/ANSWER         │
                          │              └──────────┬───────────┘
                          │              ROUTING:YES  ROUTING:NO
                          │                 │           │
                          │                 ▼           ▼
                          │            ┌────────┐ ┌────────┐
                          │            │  rag   │ │ direct │
                          │            │ 2 LLM  │ │ 1 LLM  │
                          │            │ +检索  │ │ 无检索  │
                          │            └────┬───┘ └────┬───┘
                          │                 │          │
                          ▼                 ▼          ▼
                   ┌──────────────────────────────────────────────┐
                   │              返回 Response                    │
                   │  routing ∈ {greeting, direct, rag}           │
                   │  greeting: canned 回复, 无 LLM               │
                   │  direct:   LLM 直接回答, 无检索               │
                   │  rag:      完整管道, 检索+生成                │
                   └──────────────────────────────────────────────┘

延迟量级:
  greeting: ~1ms       (纯正则, 零网络调用)
  direct:   ~0.5-2s    (1 次 LLM)
  rag:      ~2-6s      (2 次 LLM + 1 次 Embedding + 1 次 Qdrant)
```

### 摄入管道详解

摄入管道是系统最复杂的离线流程，核心设计目标是**增量更新**——第二次摄入同一个目录时，未改动的文件零成本跳过：

```
ingest_directory(input_dir)
        │
        ▼
┌──────────────────────────────────────────────┐
│ 1. _scan_files(input_dir)                    │
│    递归扫描, 匹配支持的扩展名                  │
│    .md .markdown .txt .pdf .docx             │
│    → list[Path]                              │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│ 2. ChecksumStore 分类                        │
│    逐文件 MD5 计算 → 查 SQLite               │
│                                              │
│    新文件:     SQLite 无记录 → add to new[]   │
│    变更文件:   MD5 不匹配   → add to changed[]│
│    未变更文件: MD5 匹配     → skip            │
│                                              │
│    对 changed[] 先 delete_chunks_by_filepath  │
│    （清空 Qdrant 中该文件的旧分块）           │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│ 3. _load_and_split(files_to_process)         │
│    逐文件: load_document() → Document 对象    │
│    注入 metadata: source, file_path,         │
│                  file_name, file_type, md5   │
│    split_documents() → chunks[]              │
│                                              │
│    切分策略:                                  │
│    .md/.markdown → MarkdownHeaderTextSplitter│
│                    保留 H1/H2/H3 层级         │
│    其他格式 → RecursiveCharacterTextSplitter │
│               chunk_size=800, overlap=120    │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│ 4. embed_texts(texts, batch_size=64)         │
│    调用 OpenAI 兼容 API:                     │
│    POST /v1/embeddings                       │
│    input: list[str] (64条/批)                │
│    → list[list[float]]                       │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│ 5. bulk_upsert_chunks(chunks, embeddings)    │
│    按 500 点/批拆分（避开 Qdrant 32MB 限制） │
│    Qdrant.upsert(points)                     │
│    → points_count                            │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│ 6. ChecksumStore.upsert(每文件)               │
│    更新 SQLite: file_path, md5,              │
│    chunk_count, timestamp                    │
└──────────────────────────────────────────────┘
```

两个入口共用同一管道：

| 入口 | 调用方 | 触发方式 |
|------|--------|---------|
| `ingest_file_paths()` | 上传 API (`ingestion_service.py`) | 用户通过 UI 上传文件 |
| `ingest_directory()` | CLI (`ingest.py`) | `python ingest.py --input_dir ...` |

统一的好处：上传 API 也享受增量检测（同一文件再次上传且内容未变则跳过），且 `source_map` 参数允许上传 API 保留用户看到的原始文件名。

### RAG 查询管道（逐 token 追踪）

以下以 SSE 流式端点为例，同步端点逻辑完全相同，只是用 `invoke()` 代替 `astream()`：

```
POST /rag/query/stream
Request: {question, conversation_id?, history[], force_rag?}
        │
        ▼
┌─ STEP 1 — API 层接收 (app/api/rag.py) ─────────────────────┐
│  rag_query_stream(request)                                   │
│  → 记录耗时, 透传到 service 层                               │
│  → 返回 StreamingResponse(media_type="text/event-stream")    │
└──────────────────┬──────────────────────────────────────────┘
                   │
                   ▼
┌─ STEP 2 — 查询处理 + 路由门控 (query_processor.py) ─────────┐
│                                                              │
│  ┌─ Layer 0: _check_greeting(question) ──────────────────┐  │
│  │  9 条正则规则, 4 个类别:                               │  │
│  │    greeting: hello/你好/hi/hey → canned 欢迎语         │  │
│  │    thanks:   thanks/谢谢/thank you → canned 礼貌回复   │  │
│  │    goodbye:  bye/再见/goodbye → canned 告别语          │  │
│  │    meta:     who are you/你是谁/what can you do → 说明 │  │
│  │                                                       │  │
│  │  命中 → 返回 {needs_rag: false, intent: "chitchat",   │  │
│  │               direct_answer: "..."}                    │  │
│  │  未命中 → 进入 Layer 1                                 │  │
│  └───────────────────────────────────────────────────────┘  │
│                          │ (未命中)                          │
│                          ▼                                   │
│  ┌─ Layer 1: LLM 统一路由 ───────────────────────────────┐  │
│  │  System Prompt (~60 tokens):                           │  │
│  │  ┌───────────────────────────────────────────────────┐ │  │
│  │  │ Analyze the user query for a RAG system.          │ │  │
│  │  │ Perform routing first, then act accordingly.      │ │  │
│  │  │                                                   │ │  │
│  │  │ ROUTING rules:                                    │ │  │
│  │  │ - YES: needs document search                      │ │  │
│  │  │ - NO:  answerable from general knowledge          │ │  │
│  │  │                                                   │ │  │
│  │  │ If YES → classify INTENT + rewrite QUERY          │ │  │
│  │  │ If NO  → provide direct ANSWER                    │ │  │
│  │  └───────────────────────────────────────────────────┘ │  │
│  │                                                        │  │
│  │  Input:  {question} + optional conversation history    │  │
│  │  Output:                                               │  │
│  │    ROUTING: YES|NO                                     │  │
│  │    INTENT: question_answering|summarization|...        │  │
│  │    QUERY: <rewritten query>    (if YES)                │  │
│  │    ANSWER: <direct answer>     (if NO)                 │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                              │
│  返回: {needs_rag, intent, rewritten_query, direct_answer}   │
└──────────────────┬──────────────────────────────────────────┘
                   │
        ┌──────────┴──────────┐
        │                     │
  needs_rag=false       needs_rag=true
        │                     │
        ▼                     ▼
┌─ 非 RAG 路径 ─┐    ┌─ STEP 3 — 向量检索 (retriever.py) ────┐
│                │    │                                          │
│ routing =      │    │ retrieve_relevant_documents(             │
│   "greeting"   │    │   question=rewritten_query,              │
│   或           │    │   top_k=5                                │
│   "direct"     │    │ )                                        │
│                │    │                                          │
│ SSE:           │    │ 1. CachedOpenAIEmbeddings.embed_query()  │
│  routing event │    │     ├─ LRU 命中 → 直接返回               │
│  token event   │    │     └─ 未命中 → API 调用 + 缓存          │
│  (完整答案)     │    │                                          │
│  sources: []   │    │ 2. QdrantVectorStore                     │
│  done          │    │    .similarity_search_with_score(        │

## 评估系统

`evaluation/` 目录提供完整的离线检索质量评估能力，用于在修改 embedding 模型、chunk 策略、top-k 等参数后，量化对比检索效果。

### 核心流程

```
Golden JSONL 数据集
  (22条标注问题, 含 ground-truth relevant_sources)
        │
        ▼
run_retrieval_eval.py
  ├─ 逐问题调用 production retriever
  ├─ evaluate_retrieval_case()
  │   ├─ matching: golden source → chunk ID 匹配
  │   ├─ core_metrics: Recall@K, Precision@K, MRR, NDCG@K
  │   └─ context_quality: context_redundancy@K
  └─ 输出 JSON 报告 (含 settings_snapshot)
        │
        ▼
retrieval_eval_pipeline.ipynb
  ├─ §1-15: 单实验可视化
  │   ├─ 逐问题柱状图
  │   ├─ 聚合仪表盘
  │   ├─ 雷达图 (Recall/Precision/MRR/NDCG)
  │   ├─ top-K 敏感度分析
  │   ├─ 相关性热力图
  │   └─ 自动诊断
  └─ §16: 多策略对比
      ├─ 对比表 (chunk_size, embedding_model)

      └─ 逐问题敏感度热力图

### 策略对比工作流

当需要测试不同配置（如 embedding 模型、chunk 大小）时：

```bash
# 1. 修改 .env (CHUNK_SIZE, EMBEDDING_MODEL 等)
# 2. 清空旧数据
python scripts/clear_qdrant.py && rm -f data/ingestion_state.db
# 3. 重新摄入
python ingest.py --input_dir data/engineering --batch_size 64
# 4. 评估
python evaluation/run_retrieval_eval.py \
  --dataset evaluation/datasets/golden_retrieval.example.jsonl \
  --top-k 5 \
  --experiment-name chunk800-bge-small
# 5. 重复 1-4 换配置，然后打开 notebook → Restart & Run All → 看 §16 对比
```

### 评估指标

| 指标 | 含义 | 用途 |
|------|------|------|
| Recall@K | 前 K 个结果中命中 golden 的比例 | 衡量"有没有找到" |
| Precision@K | 前 K 个结果中相关的比例 | 衡量"找得准不准" |
| MRR | 第一个相关结果的排名倒数 | 衡量"最好的答案排第几" |
| NDCG@K | 归一化折损累计增益 | 综合排名质量 |
| context_redundancy | 检索结果间的文本重复度 | 衡量"多样性" |

## API 一览

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/health` | 健康检查 |
| `GET` | `/documents` | 列出已索引文档 |
| `POST` | `/documents/upload` | 上传文档（multipart） |
| `POST` | `/documents/upload-batch` | 批量上传文档（multipart） |
| `DELETE` | `/documents/{source}` | 删除文档 |
| `POST` | `/rag/query` | RAG 问答（JSON 完整响应） |
| `POST` | `/rag/query/stream` | RAG 问答（SSE 流式响应，逐 token） |

`POST /rag/query` 请求/响应示例：

```json
// Request
{
  "question": "什么是 RAG?",
  "conversation_id": null,
  "history": [],
  "force_rag": false
}

// Response
{
  "question": "什么是 RAG?",
  "answer": "RAG 是检索增强生成...",
  "sources": [
    {
      "content": "...",
      "source": "intro.pdf",
      "file_name": "intro.pdf",
      "file_path": "data/raw/abc123.pdf",
      "chunk_index": 3,
      "page": 3,
      "score": 0.87
    }
  ],
  "conversation_id": "a1b2c3d4e5f6",
  "routing": "rag"
}
```

`POST /rag/query/stream` SSE 事件：

```
event: routing
data: {"routing":"rag","conversation_id":"a1b2c3d4e5f6"}

event: token
data: RAG

event: token
data:  是检索增强生成...

event: sources
data: [{"content":"...","source":"intro.pdf","score":0.87,...}]

event: done
data: {}
```

**Request 字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `question` | string | 是 | 用户问题（最少 1 字符） |
| `conversation_id` | string\|null | 否 | 对话 ID，null 表示新对话 |
| `history` | Message[] | 否 | 最近对话消息列表 |
| `force_rag` | boolean | 否 | 强制走 RAG 检索路径（默认 false） |

`Message` 结构：

```json
{ "role": "user" | "assistant", "content": "消息文本" }
```

**Response 字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `question` | string | 原始问题 |
| `answer` | string | LLM 生成的回答 |
| `sources` | SourceChunk[] | 检索到的文档块（非 RAG 路径为空数组） |
| `conversation_id` | string | 对话 ID（12 位 hex） |
| `routing` | string | `"rag"` \| `"direct"` \| `"greeting"` |

`routing` 取值含义：

| 值 | 含义 | LLM 调用次数 | 向量检索 |
|----|------|-------------|---------|
| `"greeting"` | 关键词预过滤命中（问候/致谢等） | 0 | 无 |
| `"direct"` | LLM 路由判断无需检索，直接回答 | 1 | 无 |
| `"rag"` | 走完整 RAG 管道（检索 + 生成） | 2 | 有 |

## 技术栈

| 层 | 技术 |
|----|------|
| 后端框架 | FastAPI + Uvicorn |
| RAG 编排 | LangChain（LCEL 管道语法） |
| 向量数据库 | Qdrant（Docker） |
| LLM | qwen3-8b-mlx（via LM Studio, OpenAI 兼容 API） |
| Embedding | text-embedding-qwen3-embedding-4b |
| 文档解析 | PyPDF (PDF), TextLoader (txt/md/markdown), Docx2txtLoader (docx) |
| 文本切分 | MarkdownHeaderTextSplitter (H1/H2/H3) + RecursiveCharacterTextSplitter (chunk=800, overlap=120) |
| 前端 | React 19 + Vite + Axios + react-markdown |
| 流式传输 | SSE (Server-Sent Events) via FastAPI StreamingResponse + LangChain astream |
| 配置 | pydantic-settings + .env |
| 摄入 | ingest.py CLI + app/rag/ingestion/ (checksum/batch embed/bulk upsert) |
| 日志 | query_logger → JSONL (logs/history/) + terminal |
| 缓存 | 线程安全内存 LRU (MD5 键, 256 条目) 用于 embedding |
| 评估 | Python CLI + Jupyter Notebook (matplotlib/seaborn/pandas) |
| 环境管理 | Conda (localrag 环境) |

## 已知问题

- `app/llm/local_llm.py` 中 provider 分支逻辑反了：`llm_provider == "local"` 时使用了 `cloud_llm_*` 配置
- `tests/` 目录下的测试文件为空骨架
- `scripts/clear_qdrant.py` 和 `scripts/ingest_sample_docs.py` 为空文件
- 无数据清理/预处理模块（文本规范化、去重等）
- 对话历史仅存前端内存，刷新页面即丢失（无后端持久化）
- 流式端点无 `response_model` 校验，需手动验证 SSE 事件数据
- 无 Re-Rank 阶段（检索后重排序）
