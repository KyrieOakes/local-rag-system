# Dev Log — 服务端上下文管理与长期记忆

> **日期**: 2026-07-31
> **标签**: feature, context-window, conversation-memory, token-budget, sqlite, rag, reliability

---

## 一、概述

本次将原有“前端截取最近 10 条消息 + 后端粗略 `len/3` 估算”的上下文机制升级为服务端统一管理的长期记忆系统。

升级后的核心能力：

- 后端根据 `conversation_id` 从 SQLite 自动恢复对话记忆，客户端不再是上下文权威来源；
- 使用“滚动摘要 + 最近原始消息”保留长期语义，同时完整原始聊天记录永不删除；
- 路由与最终回答采用统一预算策略，整体计算系统提示、问题、摘要、近期历史、检索文档、输出预留和安全余量；
- 超限时优先保留最新消息，对单条超长消息/文档做确定性截断，无法容纳当前问题时返回明确的上下文错误；
- 路由 LLM 故障时 fail-open 到 RAG，避免错误跳过知识库；
- 增加上下文用量日志、自动化测试和真实 LM Studio 冒烟验证。

## 三、后端改动

### 3.1 服务端上下文权威来源

`resolve_conversation_memory()` 的恢复顺序：

1. 有 `conversation_id` 时调用 `ConversationStore.get_context_state()`；
2. 读取长期摘要和摘要游标之后的原始消息；
3. 将浏览器传入的近期尾部与 SQLite 历史执行最长重叠匹配；
4. 只追加尚未持久化的客户端消息，避免重复；
5. SQLite 不可用或会话不存在时，降级使用客户端尾部。

客户端尾部不是长期记忆来源，其用途是覆盖以下竞态：

```text
浏览器已收到 SSE done
        ↓
用户立即发送下一条问题
        ↓
上一次后台 SQLite save_exchange 可能尚未完成
```

### 3.2 两级长期记忆

模型侧记忆由两部分组成：

```text
Earlier conversation summary
        +
Recent verbatim messages
```

完整消息仍保存在 `messages` 表中，用于 UI 展示、审计和重新生成。摘要只影响模型上下文读取游标，不删除历史数据。

默认压缩策略：

- 最近 `12` 条消息保留原文；
- 至少积累 `8` 条可压缩旧消息才触发一次摘要；
- 摘要最大 `1024` tokens；
- 摘要输入最大 `6144` tokens；
- 压缩在回答持久化后的 daemon 线程中执行；
- 摘要失败不影响回答和原始消息保存。

### 3.3 统一上下文预算

最终 LLM 输入预算：

```text
可用输入
= LLM_CONTEXT_WINDOW
- LLM_RESERVED_OUTPUT_TOKENS
- CONTEXT_SAFETY_MARGIN_TOKENS
```

可用输入继续统一分配给：

- RAG system prompt；
- 当前问题；
- 滚动摘要；
- 最近对话消息；
- 检索文档及来源 header。

默认值：

| 配置 | 默认值 | 作用 |
|------|-------:|------|
| `LLM_CONTEXT_WINDOW` | 32768 | 当前模型/服务上下文窗口 |
| `LLM_RESERVED_OUTPUT_TOKENS` | 2048 | 为回答预留并作为 `ChatOpenAI.max_tokens` |
| `CONTEXT_SAFETY_MARGIN_TOKENS` | 512 | 覆盖 tokenizer 差异和消息协议开销 |
| `CONTEXT_ROUTING_HISTORY_MAX_TOKENS` | 4096 | 路由/查询改写历史上限 |
| `CONTEXT_HISTORY_MAX_TOKENS` | 8192 | 最终生成历史上限 |
| `CONTEXT_DOCUMENT_MIN_TOKENS` | 4096 | 有文档时优先预留的检索上下文 |

裁剪顺序：

1. 保留长期摘要的一小部分预算；
2. 从最新消息向前保留完整消息；
3. 单条最新消息仍超限时，保留头尾并插入截断标记；
4. 按检索排序依次装入文档；
5. 最后一块文档可做 token 级截断；
6. 用真实渲染后的 prompt 再次校验总输入；
7. 当前问题自身无法容纳时拒绝请求，不静默截断问题。

### 3.4 离线 token 计数

默认 `CONTEXT_TOKENIZER_ENCODING=offline_multilingual`，不依赖网络：

- 中文及其他非 ASCII 字符逐字符保守计数；
- ASCII 单词按保守的 3 chars/token 计算；
- 标点逐个计数；
- 空白按块计数。

如果与模型匹配的 tiktoken 编码表已在本机缓存，可将配置改为 `cl100k_base` 等编码。编码表不可用时会自动降级到离线计数器，服务不会因为首次下载失败而中断。

### 3.5 路由故障策略

原行为：

```text
路由 LLM 异常 → needs_rag=false → 返回固定错误回答
```

新行为：

```text
路由 LLM 异常 → needs_rag=true
             → rewritten_query=原问题
             → 继续知识库检索与最终生成
```

该策略符合 RAG 系统“检索优先、故障时不漏检”的目标。

## 六、数据库改动

`conversations` 表新增：

```sql
summary                     TEXT NOT NULL DEFAULT ''
summary_through_message_id  INTEGER NOT NULL DEFAULT 0
```

启动时通过 `PRAGMA table_info(conversations)` 检查旧库；缺少列时执行 `ALTER TABLE` 原地迁移，无需删除 `data/conversations.db`。

摘要游标更新使用：

```sql
UPDATE conversations
SET summary = ?, summary_through_message_id = ?
WHERE id = ? AND summary_through_message_id < ?
```

这可以拒绝落后的后台摘要写入，防止覆盖更新的记忆状态。

Qdrant schema 和向量数据没有变化，不需要重新摄入文档。

## 九、架构决策

### 为什么服务端恢复历史

- 多客户端/API 调用行为一致；
- 刷新、切换设备或前端状态丢失不影响模型记忆；
- 预算、安全策略和日志集中在一个可信边界；
- `conversation_id` 真正成为会话状态标识，而不只是数据库分组键。

### 为什么保留完整原文而只推进摘要游标

- UI 仍能展示完整历史；
- 可以审计摘要质量；
- 摘要策略变化后可重新生成；
- 避免压缩过程造成不可逆数据损失。

### 为什么摘要异步执行

- 不增加当前回答的首 token 延迟；
- 摘要失败不阻塞主查询；
- 下一次请求在摘要尚未生成时仍可通过近期原文正常工作。

### 为什么保留安全余量

OpenAI、Qwen、DeepSeek 等模型的 tokenizer 和 ChatML 消息开销不同。安全余量用于覆盖离线估算与实际服务计数之间的偏差，避免预算恰好等于窗口上限。

## 十一、边界情况

| 场景 | 处理 |
|------|------|
| `conversation_id` 不存在 | 使用客户端尾部，首次保存时创建会话 |
| SQLite 临时读取失败 | 记录 warning，降级到客户端尾部 |
| 上一轮消息尚未落库 | 最长重叠算法追加客户端新尾部 |
| 客户端历史与服务端完全不一致 | 以服务端历史为准，避免重复/污染 |
| 最新单条消息超过历史预算 | 保留头尾，中间插入截断标记 |
| 检索文档超过剩余预算 | 保留排序靠前文档，最后一块按 token 截断 |
| 当前问题自身超过窗口 | 同步 413；SSE context error + done |
| tokenizer 编码表未缓存 | 自动使用完全离线的保守计数器 |
| 摘要 LLM 不可用 | 保留原始消息，后续周期继续尝试 |
| 并发摘要完成顺序颠倒 | 摘要游标条件更新拒绝旧写入 |
| 路由 LLM 失败 | 使用原问题继续 RAG 检索 |

## 十二、性能考虑

- SQLite 只读取当前会话摘要游标之后的消息，摘要后不会反复将全部历史送入模型；
- 摘要按批触发，不是每轮都调用 LLM；
- 摘要在后台线程执行，不增加主响应延迟；
- token 计数函数和 tiktoken encoding 使用进程内缓存；
- 文档预算沿已排序结果顺序处理，时间复杂度与候选文档数量线性相关；
- `[CONTEXT]` 日志可用于定位过度裁剪或错误的上下文窗口配置。

## 十三、对现有系统的影响

- API 成功响应结构保持兼容；
- 旧 conversation SQLite 自动迁移；
- Qdrant 与 ingestion 状态不需要重置；
- 老客户端仍可传 `history`，但服务端持久化记忆优先；
- 完整历史列表与删除 API 行为不变；
- LLM 输出现在受 `LLM_RESERVED_OUTPUT_TOKENS` 显式限制；
- 路由异常将继续走 RAG，可能比原固定错误回答多一次检索和生成，但可靠性更高。

---

## 十四、已知限制

- 离线多语言计数器是保守估算，不是 Qwen 原生 tokenizer；
- 滚动摘要依赖 LLM，摘要内容应通过评估数据持续检查忠实度；
- 当前长期记忆按对话整体摘要，不包含实体级记忆、时间衰减或用户级跨会话记忆；
- SSE 传输开始后不能再改变 HTTP 状态码，因此上下文错误使用 SSE `error` 事件表达。

---

1. 接入供应商原生 tokenizer 或 LM Studio tokenizer endpoint，减少安全余量；
